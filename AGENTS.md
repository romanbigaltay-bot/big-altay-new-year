## 1. Контекст проекта

### 1.1 Что это
Одностраничный маркетинговый лендинг (static landing page) на русском языке:
**«Новый год 2027 в Белокурихе»** — раннее бронирование новогоднего отдыха в санаториях «Белокуриха», «Сибирь» и «Катунь» (курорт «Большой Алтай», туроператор big-altay.ru).

- **Цель страницы:** конверсия посетителя в заявку (звонок 8 (800) 500-07-34 или форма → мессенджер MAX).
- **Аудитория:** частные лица, планирующие новогодний отдых семьями; мобильный трафик преобладает.
- **Язык контента:** русский. Все пользовательские строки, комментарии в коде и сообщения коммитов — на русском (допускается английский для технических идентификаторов).

### 1.2 Технологический стек
| Слой | Технология | Примечание |

| Разметка | HTML5 (`index.html`, ~1300 строк) | Семантические секции, `lang="ru"`, OG-теги, aria-атрибуты |
| Стили | CSS (vanilla, `css/style.css`, ~2900 строк) | BEM-нейминг, CSS-переменные, без препроцессоров и фреймворков |

| Деплой | GitHub Pages (branch `main`) | https://romanbigaltay-bot.github.io/big-altay-new-year/ |

**Строго запрещено без явного согласования:** добавлять npm-зависимости, фреймворки (React/Vue/jQuery), таск-раннеры, препроцессоры, CDN-библиотеки. Проект сознательно остаётся нулевой-зависимой статикой.

## 2. Модель взаимодействия с человеком

### 2.1 Основной цикл (обязателен для каждой задачи)
```
1. ПОЛУЧИТЬ ЗАДАЧУ     — заказчик формулирует цель одной задачей.
2. УТОЧНИТЬ           — если задача неоднозначна, задать 1–3 коротких вопроса
                         ДО начала работы. Не додумывать молча.
3. ВЫПОЛНИТЬ          — реализовать минимально достаточное решение.
4. ПЕРЕПРОВЕРИТЬ СЕБЯ — прогнать чек-лист верификации (раздел 4).
5. GIT-ЦИКЛ           — ветка → коммит → push → PR → merge → удалить ветку.
6. ОТЧЁТ              — структурированный отчёт в чате (раздел 2.3).
```

### 2.2 Правила общения
- **Рабочий язык — русский** (как в этом файле).
- Одна задача = один полный цикл. Не смешивать несколько задач в одном PR, если заказчик не просил иначе.
- Если задача оказалась крупнее, чем выглядела — разбить на подзадачи, озвучить план, выполнить по частям с промежуточными отчётами.
- Не оставлять заказчика с «полуготовым» состоянием: либо полная рабочая версия в main, либо ничего в main.
- Честно сообщать о невыполненном, ограничениях и допущениях. Никаких выводов «на спекуляции» — проверять фактическое состояние окружения/кода перед каждым шагом.

### 2.3 Формат финального отчёта (обязательная структура)
```markdown
## ✅ Отчёт по задаче: <название>
**Что сделано:** ... (по пунктам, что и где изменено)
**Как проверялось:** ... (конкретные команды/тесты и их результаты)
**Git:** ветка `<имя>` → PR #N (ссылка) → squash-merge → ветка удалена
**Live:** https://romanbigaltay-bot.github.io/big-altay-new-year/ (после деплоя)
**Замечания/риски:** ... (что осталось за рамками, что улучшить дальше)
**Следующий шаг:** ... (предложение, не требование)
```

### 2.4 Git-workflow (детали)
| Правило | Значение |
|---|---|
| Название ветки | `<тип>/<короткое-имя>`: `feat/...`, `fix/...`, `content/...`, `style/...`, `docs/...`, `refactor/...`, `chore/...` |
| Коммиты | Conventional Commits, описание на русском: `feat: добавлен калькулятор стоимости` |
| Тип PR | `feat` — новая функциональность, `fix` — исправления, `content` — правки текстов/цен/дат, `style` — визуальные полировки, `refactor` — рефакторинг без изменения поведения, `docs` — документация, `chore` — инфраструктура |
| Merge | **squash-merge** в `main`, затем `git push origin main` не нужен (GitHub сам), локальный `main` синхронизируется: `git checkout main && git pull` |
| После merge | Удалить ветку (локально и на GitHub) |
| Запреты | ❌ пуш напрямую в `main`; ❌ force-push в `main`; ❌ коммит секретов (токены, пароли) в любом виде |

**Авторизация в окружении:** `gh auth status` должен показывать `romanbigaltay-bot`. Токен предоставляется заказчиком через чат; после завершения сессии заказчику рекомендуется отзывать токен. Никогда не копировать токен в файлы репозитория.

### 2.5 Live-превью
- **Основной способ:** GitHub Pages — https://romanbigaltay-bot.github.io/big-altay-new-year/ (автодеплой при merge в `main`, ждать ~1 минуту).
- **Локальная проверка в окружении агента:** `python3 -m http.server 8080 --directory /workspace` (фоновый процесс) + `curl -s localhost:8080`. Встроенного браузера превью у агента нет — визуально страницу проверяют код-ревью + DOM-парсер + curl.
- После каждого merge в `main` агент обязан проверить доступность Pages: `curl -s -o /dev/null -w "%{http_code}" https://romanbigaltay-bot.github.io/big-altay-new-year/`.

## 3. Стандарты кода

### 3.1 HTML
- Семантика: каждая секция — `<section>` с `id` и `aria-label`/заголовком `h1–h3` без пропусков уровней.
- Изображения: всегда `alt`; для изображений ниже сгиба — `loading="lazy"`; указывать `width`/`height` или `height` для предотвращения CLS.
- Кнопки-действия: `<button type="button">`, ссылки-навигация: `<a href="#...">`.
- Формы: `label` привязан к `input` через `for/id`, обязательные поля помечены, `autocomplete` указан.
- Инлайновые стили в HTML — только когда это динамически управляемые значения (например, CSS-переменные из JS); декоративные инлайновые стили выносить в `style.css`.

### 3.2 CSS
- **BEM**: `блок__элемент--модификатор` (например, `.sanatorium-card__title`, `.btn--gradient-primary`).
- Цвета/отступы/радиусы — только через переменные `:root` (`--sky-*`, `--slate-*` и т.п.); хардкод палитры в правилах запрещён.
- Порядок объявления правил следует структуре файла: variables → reset/base → layout → header → hero → секции по порядку DOM → components → utilities → media queries.
- Медиа-брейкпоинты строго три: `1280px`, `1024px`, `640px`. Новые брейкпоинты — только по согласованию.
- `!important` — запрет. Глубина селекторов ≤ 3 уровней.
- Анимации: уважать `@media (prefers-reduced-motion: reduce)` (для canvas-снега есть логика остановки — см. JS).

### 3.3 JavaScript
- Один файл `js/main.js`, формат: `'use strict'` + IIFE, функции-инициализаторы `initXxx()`, вызов всех в `DOMContentLoaded`.
- Комментарий-шапка модуля в стиле `/* ===== MODULNAME ===== */` на английском технически допустим, пользовательские строки — русские.
- Обращение к DOM: `getElementById`/`querySelector` с последующим null-check; никаких глобальных переменных.
- События: делегирование там, где список элементов динамичен; обязательно снимать listeners при уничтожении компонентов (pattern для canvas).
- Производительность: тяжёлые обработчики (`resize`, `scroll`) — через debounce/rAF/IntersectionObserver (так уже сделано для снега — ориентироваться на этот паттерн).
- Запреты: `eval`, `innerHTML` для пользовательского ввода, `document.write`, синхронные XHR.
- Любая новая внешняя интеграция (отправка формы, аналитика) — через `fetch` с обработкой ошибок и fallback на toast.

### 3.4 Контент и бизнес-правила
- Даты кампании: Новый год **2027**, календарь брони — декабрь 2026 – февраль 2027.
- Санатории: ровно три — «Белокуриха», «Сибирь», «Катунь». Названия писать с кавычками-«ёлочками».
- Телефон: `8 (800) 500-07-34`, href `tel:88005000734`.
- Мессенджер: MAX, редирект на max.ru при выборе способа связи «MAX».
- Изменение цен, дат, названий, телефонов — тип коммита `content`, требует явного подтверждения цифр заказчиком.

## 4. Обязательный чек-лист верификации перед PR

Выполнить ВСЕ применимые проверки, результаты включить в отчёт:

```bash
# 1. Синтаксис JS
node --check js/main.js

# 2. Корректность HTML (все теги закрыты, вложенность валидна)
python3 - <<'EOF'
from html.parser import HTMLParser
class P(HTMLParser):
    def __init__(self):
        super().__init__(); self.stack=[]; self.err=[]
        self.void={'meta','link','br','img','hr','input','source'}
    def handle_starttag(self,t,a):
        if t not in self.void: self.stack.append(t)
    def handle_endtag(self,t):
        if not self.stack or self.stack[-1]!=t: self.err.append(t)
        else: self.stack.pop()
p=P(); p.feed(open('index.html').read())
print('OK' if not p.err and not p.stack else f'ERR {p.err[:5]} unclosed {p.stack[:5]}')
EOF

# 3. Связность: все getElementById/querySelector-иденты из JS существуют в HTML
grep -oE "getElementById\('[^']+'\)" js/main.js | sed "s/.*'\(.*\)'.*/\1/" | sort -u | \
  while read id; do grep -q "id=\"$id\"" index.html || echo "MISSING #$id"; done

# 4. Локальный запуск отдаёт 200 на все три ресурса
(python3 -m http.server 8080 --directory /workspace &>/dev/null &) ; sleep 1
for f in "" css/style.css js/main.js; do
  curl -s -o /dev/null -w "%{http_code} /$f\n" http://localhost:8080/$f; done

# 5. Нет мусора в диффе
git diff --stat main..HEAD   # интуитивно понятный размер изменений
git status                   # working tree clean после коммита
```

Дополнительно по ситуации: скриншотная проверка невозможна → перечитать изменённые участки глазами; проверить, что новые CSS-классы есть в style.css, новые id — в HTML.

## 5. Документирование решений (AI Engineering practices)

- **Неочевидные решения** (почему выбран самописный календарь вместо библиотеки, почему fake-submit) фиксировать в комментариях рядом с кодом и в описании PR.
- **Известные технические долги** (см. README «Планы») обновлять по мере закрытия — удалять пункт из долга и переносить в историю.
- **Описание PR** — по шаблону: что / зачем / как проверялось / что под вопросом.
- **Согласование с реальностью:** перед каждой новой задачей агент перечитывает актуальное состояние репозитория (`git pull`, `ls`), не полагаясь на память прошлых сессий — контекст между сессиями может теряться.

## 6. Эскалация и границы полномочий
