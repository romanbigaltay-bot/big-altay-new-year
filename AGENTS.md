## 1. Контекст проекта

Одностраничный маркетинговый лендинг (static landing page) на русском языке:
**«Новый год 2027 в Белокурихе»** — раннее бронирование новогоднего отдыха в санаториях «Белокуриха», «Сибирь» и «Катунь» (курорт «Большой Алтай», туроператор big-altay.ru).

## 2. Модель взаимодействия с человеком

### 2.1 Основной цикл (обязателен для каждой задачи)
```
1. ПОЛУЧИТЬ ЗАДАЧУ     — заказчик формулирует цель одной задачей.
2. УТОЧНИТЬ           — если задача неоднозначна, задать 1–3 коротких вопроса
                         ДО начала работы. Не додумывать молча.
3. ВЫПОЛНИТЬ          — реализовать минимально достаточное решение.
4. ПЕРЕПРОВЕРИТЬ СЕБЯ — прогнать чек-лист верификации (раздел 4).
5. GIT-ЦИКЛ           — ветка → коммит → push → PR → merge → удалить ветку.
6. ОТЧЁТ              — структурированный отчёт в чате (раздел 2.3).
```

### 2.2 Правила общения
- **Рабочий язык — русский** (как в этом файле).
- Одна задача = один полный цикл. Не смешивать несколько задач в одном PR, если заказчик не просил иначе.
- Если задача оказалась крупнее, чем выглядела — разбить на подзадачи, озвучить план, выполнить по частям с промежуточными отчётами.
- Не оставлять заказчика с «полуготовым» состоянием: либо полная рабочая версия в main, либо ничего в main.
- Честно сообщать о невыполненном, ограничениях и допущениях. Никаких выводов «на спекуляции» — проверять фактическое состояние окружения/кода перед каждым шагом.

### 2.2.1 Протокол «доведённого git-цикла» (ОБЯЗАТЕЛЬНЫЙ, пошаговый)

Задача со изменением кода считается выполненной **только когда результат верифицирован на живом GitHub Pages**. Заказчик тестирует боевую сборку Pages; любое отчёта без фактического пуша/PR = провал = потеря доверия (прецеденты: §2.2.2).

Главный принцип: **каждый шаг подтверждается выводом команды, а не ожиданием «должно сработать».** Пустой вывод, ошибка или молчание — это НЕ успех. Любое утверждение в отчёте («смержено», «задеплоено», «PR #N») допускается только после того, как соответствующая команда реально выполнилась и её вывод скопирован/прочитан.

#### Шаг 0. Проверка окружения (ВСЕГДА в начале задачи, до редактирования кода)
```bash
git -C /workspace status --short && git -C /workspace log --oneline -1
git -C /workspace fetch origin && git -C /workspace rev-parse HEAD origin/main  # локальный main == origin/main?
python3 - <<'EOF'   # проверка токена к GitHub API (gh CLI может отсутствовать после рестарта контейнера)
import re, urllib.request, json
raw=open('/root/.git-credentials').read()
tok=re.search(r'https://[^:]+:([^@]+)@github\.com',raw).group(1)
r=json.load(urllib.request.urlopen(urllib.request.Request('https://api.github.com/user',headers={'Authorization':f'Bearer {tok}'})))
print('AUTH OK:',r['login'])
EOF
```
- Окружение перезапускается между сообщениями: `gh` может пропасть, но токен живёт в `~/.git-credentials`. Рабочий инструмент по умолчанию — **Python/curl + GitHub REST API**; `gh` — опционально, если установлен.
- Если авторизация падает (401) — починить её ДО начала работы, а не в конце.

#### Шаг 1. Изменение кода + локальная верификация
Внести правки, прогнать проверки (§4 чек-лист: node --check, парсер HTML, связность id/class). Только затем:
```bash
git checkout -b <тип>/<slug>
git add -A && git commit -m "<тип>: <описание>"
git status --short            # ОБЯЗАТЕЛЬНО пусто — иначе изменения не в коммите!
```

#### Шаг 2. Push и подтверждение, что ветка на GitHub
```bash
git push -u origin <ветка>
# Подтверждение (не верить exit code пуша, спросить GitHub):
git ls-remote --heads origin <ветка>   # должен вернуть SHA
```

#### Шаг 3. Создание PR — номер берём ТОЛЬКО из ответа API
```bash
# POST /repos/{owner}/{repo}/pulls → прочитать response["number"] и response["html_url"]
```
- **Запрещено придумывать/предполагать номер PR.** Номер и ссылка — только из тела успешного JSON-ответа (`"merged": true` у merge-запроса тоже читается из ответа).
- После создания: GET `/pulls/N` → убедиться `state != closed` ошибочный, base = main.

#### Шаг 4. Merge + подтверждение
```bash
# PUT /repos/{owner}/{repo}/pulls/N/merge (merge_method=squash) → HTTP 200 и "merged": true
git fetch origin main
git rev-parse origin/main     # SHA squash-коммита должен СОВПАСТЬ с expected
```

#### Шаг 5. Верификация удалённого репо (НЕ локального!)
```bash
curl -s https://raw.githubusercontent.com/romanbigaltay-bot/big-altay-new-year/main/<файл> | grep -c "<маркер изменения>"
```
Маркер — уникальная строка именно этого изменения. Результат ≥1. Иначе — шаг не пройден.

#### Шаг 6. Верификация живого Pages
```bash
curl -s "https://romanbigaltay-bot.github.io/big-altay-new-year/<файл>?cb=$(date +%s)" | grep -c "<маркер>"
```
Сборка Pages отстаёт на 30–120 секунд: если маркер не найден — подождать и повторить (до ~3 минут), а не рапортовать об успехе.

#### Шаг 7. Уборка
Удалить feature-ветку (локально и на GitHub), синхронизировать локальный main с origin, `git status` — clean.

#### Жёсткие запреты
- ❌ Писать «готово / смержено / PR #N» без фактических выводов шагов 2–6 в текущем ответе.
- ❌ Называть ссылку на PR/коммит, которая не открылась бы (номер из воздуха = 404 у заказчика).
- ❌ Перекладывать git-цикл на заказчика («напиши „доведи пуш“»). Цикл исполняется агентом до конца в той же задаче; если инструментов не хватило — продолжить при первой возможности и НЕ объявлять задачу закрытой.
- ❌ Основываться на «я вроде делал раньше» — состояние окружения проверяется заново каждый раз (Шаг 0).
- ✅ В финальном отчёте указывать фактические SHA/номера, полученные из ответов команд, и напоминать о Ctrl+Shift+R.

### 2.2.2 Прецеденты (чтобы не повторять)
- **PR #4/#5:** написал «готово», файлы остались в staging → заказчик тестировал старый код на Pages. Причина: не выполнен Шаг 1 (`git status` не пустой) и Шаги 5–6.
- **PR #11/#12/#13 (трижды!):** заявлял несуществующие номера PR (#12, #13 → 404) и «успешный merge» без реальных вызовов API; фактический merge #11 произошёл раньше, новые правки (например, переписанный §2.2.1) вообще не были закоммичены. Причина: отчёт «на спекуляции» вместо Шагов 3–6; gh CLI умер после рестарта контейнера, а альтернатива (REST API) не была задействована. Исправлено этим документом + реальным циклом PR #12.
- **Вывод:** пустой/отсутствующий вывод инструмента трактуется как неудача; любой успех подтверждается перечитыванием состояния из источника истины (GitHub API/raw/Pages), а не памяти о намерениях.

### 2.3 Формат финального отчёта (обязательная структура)
```markdown
## ✅ Отчёт по задаче: <название>
**Что сделано:** ... (по пунктам, что и где изменено)
**Как проверялось:** ... (конкретные команды/тесты и их результаты)
**Git:** ветка `<имя>` → PR #N (ссылка) → squash-merge → ветка удалена
**Live:** https://romanbigaltay-bot.github.io/big-altay-new-year/ (после деплоя)
**Замечания/риски:** ... (что осталось за рамками, что улучшить дальше)
**Следующий шаг:** ... (предложение, не требование)
```

### 2.4 Git-workflow (детали)
| Правило | Значение |
|---|---|
| Название ветки | `<тип>/<короткое-имя>`: `feat/...`, `fix/...`, `content/...`, `style/...`, `docs/...`, `refactor/...`, `chore/...` |
| Коммиты | Conventional Commits, описание на русском: `feat: добавлен калькулятор стоимости` |
| Тип PR | `feat` — новая функциональность, `fix` — исправления, `content` — правки текстов/цен/дат, `style` — визуальные полировки, `refactor` — рефакторинг без изменения поведения, `docs` — документация, `chore` — инфраструктура |
| Merge | **squash-merge** в `main`, затем `git push origin main` не нужен (GitHub сам), локальный `main` синхронизируется: `git checkout main && git pull` |
| После merge | Удалить ветку (локально и на GitHub) |
| Запреты | ❌ пуш напрямую в `main`; ❌ force-push в `main`; ❌ коммит секретов (токены, пароли) в любом виде |

**Авторизация в окружении:** `gh auth status` должен показывать `romanbigaltay-bot`. Токен предоставляется заказчиком через чат; после завершения сессии заказчику рекомендуется отзывать токен. Никогда не копировать токен в файлы репозитория.

### 2.5 Live-превью
- **Основной способ:** GitHub Pages — https://romanbigaltay-bot.github.io/big-altay-new-year/ (автодеплой при merge в `main`, ждать ~1 минуту).
- **Локальная проверка в окружении агента:** `python3 -m http.server 8080 --directory /workspace` (фоновый процесс) + `curl -s localhost:8080`. Встроенного браузера превью у агента нет — визуально страницу проверяют код-ревью + DOM-парсер + curl.
- После каждого merge в `main` агент обязан проверить доступность Pages: `curl -s -o /dev/null -w "%{http_code}" https://romanbigaltay-bot.github.io/big-altay-new-year/`.

## 3. Стандарты кода

### 3.1 HTML
- Семантика: каждая секция — `<section>` с `id` и `aria-label`/заголовком `h1–h3` без пропусков уровней.
- Изображения: всегда `alt`; для изображений ниже сгиба — `loading="lazy"`; указывать `width`/`height` или `height` для предотвращения CLS.
- Кнопки-действия: `<button type="button">`, ссылки-навигация: `<a href="#...">`.
- Формы: `label` привязан к `input` через `for/id`, обязательные поля помечены, `autocomplete` указан.
- Инлайновые стили в HTML — только когда это динамически управляемые значения (например, CSS-переменные из JS); декоративные инлайновые стили выносить в `style.css`.

### 3.2 CSS
- **BEM**: `блок__элемент--модификатор` (например, `.sanatorium-card__title`, `.btn--gradient-primary`).
- Цвета/отступы/радиусы — только через переменные `:root` (`--sky-*`, `--slate-*` и т.п.); хардкод палитры в правилах запрещён.
- Порядок объявления правил следует структуре файла: variables → reset/base → layout → header → hero → секции по порядку DOM → components → utilities → media queries.
- Медиа-брейкпоинты строго три: `1280px`, `1024px`, `640px`. Новые брейкпоинты — только по согласованию.
- `!important` — запрет. Глубина селекторов ≤ 3 уровней.
- Анимации: уважать `@media (prefers-reduced-motion: reduce)` (для canvas-снега есть логика остановки — см. JS).

### 3.3 JavaScript
- Один файл `js/main.js`, формат: `'use strict'` + IIFE, функции-инициализаторы `initXxx()`, вызов всех в `DOMContentLoaded`.
- Комментарий-шапка модуля в стиле `/* ===== MODULNAME ===== */` на английском технически допустим, пользовательские строки — русские.
- Обращение к DOM: `getElementById`/`querySelector` с последующим null-check; никаких глобальных переменных.
- События: делегирование там, где список элементов динамичен; обязательно снимать listeners при уничтожении компонентов (pattern для canvas).
- Производительность: тяжёлые обработчики (`resize`, `scroll`) — через debounce/rAF/IntersectionObserver (так уже сделано для снега — ориентироваться на этот паттерн).
- Запреты: `eval`, `innerHTML` для пользовательского ввода, `document.write`, синхронные XHR.
- Любая новая внешняя интеграция (отправка формы, аналитика) — через `fetch` с обработкой ошибок и fallback на toast.

### 3.4 Контент и бизнес-правила
- Даты кампании: Новый год **2027**, календарь брони — декабрь 2026 – февраль 2027.
- Санатории: ровно три — «Белокуриха», «Сибирь», «Катунь». Названия писать с кавычками-«ёлочками».
- Телефон: `8 (800) 500-07-34`, href `tel:88005000734`.
- Мессенджер: MAX, редирект на max.ru при выборе способа связи «MAX».
- Изменение цен, дат, названий, телефонов — тип коммита `content`, требует явного подтверждения цифр заказчиком.
- **Цены не отображаются на лендинге — это осознанное продуктовое решение** (стоимость отвлекает от ценности; расчёт цены происходит в процессе продажи через менеджера). Не предлагать калькуляторы стоимости, прайсы и вывод цен в UI. Идея «калькулятора» из начала разработки закрыта; историческая секция переименована в якорь `#booking` (классы `.section--booking`, `.booking-card` и т.д.).
- **Интеграция заявок (прод):** обе формы шлют JSON на серверный прокси `server.php` (корень сайта; принимает заявку → создаёт лид в Bitrix24 через `crm.lead.add`). Клиентский код — `js/bitrix.js`, API `window.BigAltayCRM` (`submitLead(payload)`, мапперы форм). Секретный webhook живёт ТОЛЬКО на сервере (`config.local.php`) — запрещать появление webhook-URL в любом публичном коде боевой сборки. Маппинг полей менять только вместе с CRM-администратором. Защита прокси: CORS allow-list, honeypot (`site_email`), rate-limit, валидация. При добавлении нового боевого домена — обновить `$ALLOWED_ORIGINS`.
- **Интеграция заявок (дев-полигон GitHub Pages):** PHP там недоступен, поэтому для ручной проверки форм подключён `js/dev-leads.js` — временный dev-only модуль с обфусцированным (XOR + base64) ТЕСТОВЫМ webhook, подменяющим транспорт `BigAltayCRM.submitLead` на прямые вызовы REST. Это осознанное исключение из правила «секрет только на сервере», разрешённое владельцем проекта для тестового webhook'а с коротким жизненным циклом. ПЕРЕД ДЕПЛОЕМ НА BEGET: удалить файл `js/dev-leads.js` и его `<script>` в `index.html` (помечено комментарием DEV-ONLY), отозвать тестовый webhook и создать боевой. Проверять статус этого пункта в README (чек-лист «Перед боевым запуском»).
- **Формат лида в CRM (согласовано с заказчиком, PR #5 → #6 → #7):** TITLE = `Имя | Контакт — Новый год 2027 · Санаторий «X»` (например, `Мария | +7 913 987-95-55 — Новый год 2027 · Санаторий «Сибирь»`). Ярлыки вида «Заявка с лендинга», «Форма бронирования» в TITLE запрещены — лишняя информация; контекст формы и страницы передаётся отдельным полем `SOURCE_DESCRIPTION` и комментариями в таймлайне. В таймлайн (`crm.timeline.comment.add`) падают все детали заявки. **Новогодняя программа:** пользователь выбирает её кнопкой «Выбрать эту программу» в карточке секции `#programs` (`data-program-title`); кнопка подставляет название программы текстом в поле «Пожелания / Вопросы» (`#bookingComment`, строка «Новогодняя программа: …») — отдельные hidden-поля для программы запрещены решением заказчика. Программа НЕ попадает в TITLE.

## 4. Обязательный чек-лист верификации перед PR

Выполнить ВСЕ применимые проверки, результаты включить в отчёт:

```bash

from html.parser import HTMLParser
class P(HTMLParser):
    def __init__(self):
        super().__init__(); self.stack=[]; self.err=[]
        self.void={'meta','link','br','img','hr','input','source'}
    def handle_starttag(self,t,a):
        if t not in self.void: self.stack.append(t)
    def handle_endtag(self,t):
        if not self.stack or self.stack[-1]!=t: self.err.append(t)
        else: self.stack.pop()
p=P(); p.feed(open('index.html').read())
print('OK' if not p.err and not p.stack else f'ERR {p.err[:5]} unclosed {p.stack[:5]}')
EOF
```

## 5. Документирование решений (AI Engineering practices)

- **Неочевидные решения** (почему выбран самописный календарь вместо библиотеки, почему fake-submit) фиксировать в комментариях рядом с кодом и в описании PR.
- **Известные технические долги** (см. README «Планы») обновлять по мере закрытия — удалять пункт из долга и переносить в историю.
- **Описание PR** — по шаблону: что / зачем / как проверялось / что под вопросом.
- **Согласование с реальностью:** перед каждой новой задачей агент перечитывает актуальное состояние репозитория (`git pull`, `ls`), не полагаясь на память прошлых сессий — контекст между сессиями может теряться.
